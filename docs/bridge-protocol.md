# Local bridge protocol v1 (specification)

**Status:** framing implemented and unit-tested in Rust; transport, authentication, rendering and input forwarding are not implemented.

## Transport and security requirements

- The initial transport candidate is a local TCP connection bound explicitly to IPv4 loopback (`127.0.0.1`), not `0.0.0.0` or a LAN interface.
- The Android app must not treat a successful TCP connection as authentication. The first application message must prove possession of a fresh, high-entropy, per-session token generated by the Termux launcher.
- Generate at least 32 random bytes from the operating system CSPRNG for each session. Do not reuse tokens across launches, put them in exported intents, command-line arguments, logs, or persistent preferences.
- Compare authentication tokens in constant time. Reject failed authentication and close the connection. Add a handshake timeout and an idle timeout before implementing a listener.
- Loopback reachability between Termux and the Android app is device/ROM dependent and must be tested. If it is blocked, do not fall back to a public listener; evaluate an explicitly paired Unix-domain socket or another scoped IPC mechanism.
- Do not enable clipboard or input forwarding before authentication succeeds.

## Frame format

All integer fields are unsigned, big-endian. Every message begins with a 12-byte header:

| Offset | Size | Meaning |
|---:|---:|---|
| 0 | 4 | ASCII magic `TXWB` |
| 4 | 1 | Protocol version (`1`) |
| 5 | 1 | Message kind |
| 6 | 2 | Reserved; must be zero |
| 8 | 4 | Payload length, excluding header |

Payloads are limited to 16 MiB. Receivers must validate the header and length before allocating the payload. Unknown kinds, unsupported versions, nonzero reserved bits, truncated messages and oversized payloads are errors; close the connection on protocol errors. The current Rust module implements this framing and enforces these bounds.

## Message kinds

| Value | Name | Direction | Purpose |
|---:|---|---|---|
| 1 | `HELLO` | Android → Termux | Authentication token (exactly 32 bytes) |
| 2 | `WELCOME` | Termux → Android | Session accepted; initial v1 payload is empty |
| 3 | `FRAME` | Termux → Android | Frame metadata followed by pixel bytes |
| 4 | `INPUT` | Android → Termux | Input event record |
| 5 | `RESIZE` | Android → Termux | Requested logical surface dimensions |
| 6 | `CLIPBOARD` | Bidirectional | UTF-8 text, bounded separately before clipboard use |
| 7 | `PING` | Bidirectional | Liveness probe |
| 8 | `PONG` | Bidirectional | Liveness response |
| 9 | `CLOSE` | Bidirectional | Graceful session close |

## Initial payload conventions

These are protocol conventions for the next implementation phase; only the generic message envelope is implemented at present.

- `HELLO`: exactly 32 bytes of session token. Never log payload bytes.
- `WELCOME`: empty payload.
- `FRAME`: width (`u16`), height (`u16`), pixel format (`u8`, initially `1` = RGBA8888), three reserved zero bytes, then `width × height × 4` bytes. Validate dimensions and exact payload length before rendering. The 16 MiB envelope cap means large frames must later be tiled or compressed rather than bypassing the limit.
- `RESIZE`: width (`u16`) and height (`u16`); reject zero dimensions and values beyond implementation limits.
- `CLIPBOARD`: UTF-8 bytes, maximum 1 MiB, only after explicit session authentication. Do not automatically execute clipboard contents.
- `PING`, `PONG`, `CLOSE`: empty payloads in version 1.
- `INPUT`: remains to be specified with explicit event types, coordinate bounds, pointer/button state, key representation, and input-rate limits before it is enabled.

## Compatibility and testing

The Android client and Termux process must agree on protocol version and endianness. Add shared golden test vectors before implementing the Android decoder. Unit tests currently cover round trips and rejection of bad magic, unsupported versions, unknown kinds, nonzero reserved bits and payload lengths above the cap.

A successful `WELCOME` may change UI state to connected only after the complete authenticated handshake succeeds. A connected state must be cleared on socket close, timeout, app pause/reconnect failure, or `CLOSE`.
